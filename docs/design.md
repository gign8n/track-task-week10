# Design: ระบบติดตามงานทีม

เอกสารนี้ออกแบบจาก [plan.md](plan.md) และ [requirements.md](requirements.md) โดยไม่เปลี่ยนข้อกำหนด ใช้เป็นแบบสำหรับพัฒนาและตรวจตามเลข US / AC (เรื่องที่ผู้ใช้ต้องทำได้ / เกณฑ์ยอมรับ)

## 1. ขอบเขตและโครงสร้างระบบ

- งานหลัก: US-1 → US-2 → US-3 → US-4 ตามลำดับ งานเสริม: US-5 → US-6
- ใช้ Next.js 16 App Router, TypeScript และ Tailwind ตามโปรเจกต์ หน้าเว็บติดต่อ Supabase ผ่านตัวเชื่อมที่มีใน lib/supabase/ และนำเว็บขึ้น Vercel
- Supabase Auth ดูแลบัญชีและการล็อกอิน ส่วน Postgres เก็บข้อมูล และ RLS (กฎจำกัดสิทธิ์รายแถว) ป้องกันข้อมูลข้ามทีม แม้เรียกฐานข้อมูลโดยไม่ผ่านหน้าเว็บ
- ฝั่ง server (ส่วนที่ทำงานบนเครื่องบริการ) ตรวจผู้ใช้ด้วย supabase.auth.getUser() หรือ getClaims() ทุกคำขอที่ต้องล็อกอิน ไม่เชื่อ user_id หรือบทบาทจากฟอร์ม
- ใช้ publishable key และสถานะล็อกอินของผู้เรียกทั้งฝั่งเบราว์เซอร์และ server ไม่ใช้ Supabase secret key
- proxy.ts รีเฟรช session (สถานะล็อกอิน) ตามโครงเดิม ใช้คุกกี้ที่คงอยู่เมื่อปิดเบราว์เซอร์เพื่อรองรับ AC-1.4 ไม่เปิด Cache Components และไม่เก็บข้อมูลส่วนบุคคลในแคชที่แชร์ข้ามผู้ใช้
- ขั้นนี้จัดทำเอกสารเท่านั้น ยังไม่สร้างโค้ดแอปหรือรัน SQL คำสั่งเปลี่ยนฐานข้อมูลในอนาคตต้องอยู่ใน supabase/migrations/ และให้ผู้ใช้รันเอง

## 2. แบบข้อมูล (Data model)

PK คือคีย์ระบุแถวไม่ซ้ำ, FK คือคีย์เชื่อมตาราง, unique คือข้อบังคับห้ามซ้ำ และ NOT NULL คือห้ามเว้นค่า เวลาบันทึกใช้ timestamptz (เวลาที่มีเขตเวลา) ส่วนวันกำหนดส่งใช้ date (วันที่ไม่มีเวลา)

### profiles — ข้อมูลแสดงของผู้ใช้ (US-1, US-2, US-6)

| คอลัมน์ | ชนิด | ข้อบังคับ / ความหมาย |
|---|---|---|
| user_id | uuid | PK, FK → auth.users(id); ลบตามเมื่อบัญชีถูกลบ แต่การลบบัญชีที่ยังเกี่ยวกับทีม/งานถูก FK อื่นป้องกันไว้ |
| display_name | text | NOT NULL, ตัดช่องว่างแล้วต้องไม่ว่าง |
| email | text | NOT NULL, สำเนาอีเมลจาก auth.users; ผู้ใช้ส่งค่าเองเพื่อแก้ตารางนี้ไม่ได้ |
| created_at | timestamptz | NOT NULL, default now() |

สร้าง profile ด้วย trigger (การทำงานอัตโนมัติเมื่อข้อมูลเปลี่ยน) หลังสร้าง auth.users ในธุรกรรมเดียวกัน อ่านชื่อจากข้อมูลสมัครและตรวจซ้ำในฐานข้อมูล ถ้าสร้าง profile ไม่ได้ให้การสมัครล้มเหลวทั้งหมด ไม่ทิ้งบัญชีที่ไม่มีชื่อ อีเมลคัดลอกจาก auth.users เท่านั้น และซิงก์เมื่ออีเมลใน Auth เปลี่ยน ไม่อ่านอีเมลจาก user metadata ที่เจ้าของบัญชีแก้เองได้ ไม่มีหน้าจอแก้ profile ในรอบนี้

### teams — ทีม (US-2)

| คอลัมน์ | ชนิด | ข้อบังคับ / ความหมาย |
|---|---|---|
| id | uuid | PK, default gen_random_uuid() |
| name | text | NOT NULL, ตัดช่องว่างแล้วต้องไม่ว่าง |
| owner_id | uuid | NOT NULL, FK → profiles(user_id), unique; ผู้สร้างและหัวหน้าคนเดียวของทีม |
| invite_code | text | NOT NULL, unique, รูปแบบตัวอักษรอังกฤษใหญ่/ตัวเลข 6 ตัว |
| created_at | timestamptz | NOT NULL, default now() |

รหัสสร้างจากการสุ่มฝั่งฐานข้อมูล ไม่ใช้เลขเรียง หากชน unique ให้สุ่มใหม่ ห้ามเก็บรหัสใน URL หรือบันทึกลง log (บันทึกการทำงาน) ของแอป

### team_members — สมาชิกทีม (US-2)

| คอลัมน์ | ชนิด | ข้อบังคับ / ความหมาย |
|---|---|---|
| user_id | uuid | PK, FK → profiles(user_id); PK นี้บังคับว่า 1 คนอยู่ได้เพียง 1 ทีม |
| team_id | uuid | NOT NULL, FK → teams(id) |
| joined_at | timestamptz | NOT NULL, default now() |

เพิ่ม unique(team_id, user_id) สำหรับให้ตารางอื่นอ้างคู่ทีมและสมาชิก บทบาทคำนวณจาก teams.owner_id = team_members.user_id จึงไม่มีคอลัมน์ role ที่อาจขัดกับผู้สร้างทีม

เพิ่ม FK คู่ (teams.id, teams.owner_id) → team_members(team_id, user_id) แบบ DEFERRABLE INITIALLY DEFERRED (ตรวจตอนจบธุรกรรม) เพื่อรับประกันว่าหัวหน้าเป็นสมาชิกทีมตัวเอง การสร้างทีมและเพิ่มหัวหน้าจึงต้องสำเร็จพร้อมกัน ห้ามเปลี่ยน owner_id หลังสร้างในรอบนี้

### tasks — งาน (US-3, US-4, US-5, US-6)

| คอลัมน์ | ชนิด | ข้อบังคับ / ความหมาย |
|---|---|---|
| id | uuid | PK, default gen_random_uuid() |
| team_id | uuid | NOT NULL, FK → teams(id) |
| title | text | NOT NULL, ตัดช่องว่างแล้วต้องไม่ว่าง |
| description | text | ไม่บังคับ; ช่องว่างล้วนเก็บเป็น NULL |
| due_date | date | ไม่บังคับ; NULL หมายถึงไม่มีกำหนด อนุญาตวันในอดีต |
| assignee_id | uuid | NOT NULL, FK คู่ (team_id, assignee_id) → team_members(team_id, user_id) |
| created_by | uuid | NOT NULL, FK คู่ (team_id, created_by) → team_members(team_id, user_id); กำหนดจาก auth.uid() ตอนสร้าง |
| status | text | NOT NULL, default todo, CHECK ให้อยู่ใน todo / in_progress / done เท่านั้น |
| created_at | timestamptz | NOT NULL, default now() |
| updated_at | timestamptz | NOT NULL, default now(); ฐานข้อมูลเป็นผู้ตั้งเมื่ออัปเดต |

สถานะบนหน้าจอ: todo = ยังไม่เริ่ม, in_progress = กำลังทำ, done = เสร็จแล้ว ไม่เก็บ is_overdue (เลยกำหนดหรือไม่) เพราะเปลี่ยนตามวัน

ความสัมพันธ์: ผู้ใช้ 1 คนมี profile 1 แถว และสมาชิกทีมได้ 0 หรือ 1 แถว; ทีมมีสมาชิกหลายคนและงานหลายชิ้น; งานมีผู้รับ 1 คนซึ่งต้องอยู่ทีมเดียวกัน หัวหน้ารับงานเองได้

เพิ่มดัชนี (ตัวช่วยค้นข้อมูล) ที่ team_members(team_id), tasks(team_id, status), tasks(assignee_id, due_date) ไม่เปิดการลบทีม/สมาชิก/บัญชีผ่านแอป และใช้ FK แบบปฏิเสธการลบข้อมูลที่ยังถูกอ้างถึง เพื่อไม่ให้งานหรือหัวหน้าหายโดยไม่ตั้งใจ

## 3. ตารางสิทธิ์ ใช้เป็นแบบของ RLS

เปิด RLS ทุกตารางใน public และกำหนดสิทธิ์ฐานตารางให้สอดคล้องกัน นโยบาย SELECT ใช้ตรวจแถวที่อ่านได้, UPDATE ต้องตรวจทั้งแถวเดิมและแถวใหม่ด้วย USING / WITH CHECK ส่วนการแก้รายคอลัมน์ใช้ trigger เพิ่มเติม เพราะ RLS อย่างเดียวไม่พอ

✓ = อนุญาตตามเงื่อนไข, – = ไม่อนุญาตโดยตรง, function = เรียกฟังก์ชันที่ตรวจสิทธิ์ก่อนทำงาน ตารางนี้หมายถึงการเรียกด้วย publishable key และสถานะผู้ใช้ ไม่ใช่สิทธิ์ผู้ดูแลฐานข้อมูล

| ตาราง | บทบาท / ความสัมพันธ์กับแถว | select | insert | update | delete |
|---|---|---|---|---|---|
| profiles | anon (ยังไม่ล็อกอิน) | – | – | – | – |
| profiles | เจ้าของ profile รวมผู้ยังไม่มีทีม | ✓ เฉพาะตนเอง | – | – | – |
| profiles | หัวหน้าหรือสมาชิกทีมเดียวกับเจ้าของ profile | ✓ ชื่อและอีเมลในทีม | – | – | – |
| profiles | ผู้ใช้คนอื่น / คนนอกทีม | – | – | – | – |
| teams | anon | – | – | – | – |
| teams | ผู้ล็อกอินที่ยังไม่มีทีม | – | function create_team | – | – |
| teams | หัวหน้าเจ้าของทีม | ✓ ทีมตัวเอง | – | – | – |
| teams | สมาชิกทีม | ✓ ทีมตัวเอง รวมรหัสเชิญ | – | – | – |
| teams | คนนอกทีม / หัวหน้าทีมอื่น | – | – | – | – |
| team_members | anon | – | – | – | – |
| team_members | ผู้ล็อกอินที่ยังไม่มีทีม | – | function create_team / join_team | – | – |
| team_members | หัวหน้าทีม | ✓ สมาชิกทีมตัวเอง | – | – | – |
| team_members | สมาชิกทีม | ✓ สมาชิกทีมตัวเอง | – | – | – |
| team_members | คนนอกทีม | – | – | – | – |
| tasks | anon | – | – | – | – |
| tasks | ผู้ล็อกอินที่ยังไม่มีทีม / คนนอกทีม | – | – | – | – |
| tasks | หัวหน้าทีมของงาน | ✓ | ✓ | ✓ ฟิลด์เนื้องาน | – |
| tasks | ผู้รับงานที่ไม่ใช่หัวหน้า | ✓ | – | ✓ เฉพาะ status | – |
| tasks | สมาชิกทีมที่ไม่ได้รับงาน | ✓ | – | – | – |

- การอ่าน profile ของตัวเองไม่ทำให้เห็น profile ของคนนอกทีม (AC-2.6) ส่วนอีเมลเพื่อนร่วมทีมอ่านได้ตามขอบเขตใน plan.md
- profiles เขียนได้เฉพาะ trigger ที่ซิงก์จาก Auth; teams และ team_members เขียนผ่านฟังก์ชันที่กำหนดเท่านั้น ไม่ให้สิทธิ์เขียนตรงแม้เป็นหัวหน้า
- หัวหน้าแก้ title, description, due_date, assignee_id และ status ได้ในระดับฐานข้อมูลตาม plan.md แต่ไม่มีฟอร์มแก้ไขในรอบนี้ id, team_id, created_by, created_at เปลี่ยนไม่ได้ และ updated_at ให้ฐานข้อมูลจัดการ
- ไม่มี DELETE policy สำหรับผู้ใช้แอป หากจำเป็นต้องลบงานตาม plan.md ให้ผู้มีสิทธิ์ดูแลโปรเจกต์ดำเนินการใน Supabase Table Editor ซึ่งเป็นสิทธิ์ดูแลฐานข้อมูล ไม่ใช่บทบาทหัวหน้าทีมบนเว็บ ต้องตรวจทีม/งานให้ถูกก่อนลบ

## 4. ฟังก์ชันฐานข้อมูลและการเข้าถึงก่อนเป็นสมาชิก

RPC คือการเรียกฟังก์ชันในฐานข้อมูลจากแอป ส่วน SECURITY DEFINER คือฟังก์ชันที่ทำงานด้วยสิทธิ์เจ้าของ จึงต้องตรวจผู้เรียกภายในอย่างเคร่งครัด

| ฟังก์ชัน | ผู้เรียก / ข้อมูลเข้า | การทำงานและผลลัพธ์ | อ้างอิง |
|---|---|---|---|
| create_team(name) | ผู้ล็อกอิน; รับเฉพาะชื่อทีม | ตรวจผู้ใช้และชื่อ สร้างทีมพร้อมเพิ่มหัวหน้า คืน team_id เมื่อสำเร็จ | AC-2.1, AC-2.2, AC-2.4, AC-2.5 |
| join_team(invite_code) | ผู้ล็อกอิน; รับเฉพาะรหัสเชิญ | ตัดช่องว่าง/แปลงเป็นตัวใหญ่ ตรวจรหัสและเพิ่มสมาชิก คืน team_id หลังเข้าร่วมสำเร็จ | AC-2.3, AC-2.4, AC-2.6 |
| private.current_team_id() | ใช้ใน policy | คืนเฉพาะทีมของ auth.uid() หรือ NULL ไม่รับ user_id จากผู้เรียก | AC-2.6, AC-3.7 |
| private.is_team_owner(team_id) | ใช้ใน policy / trigger | คืนว่าผู้เรียกเป็นหัวหน้าทีมนี้หรือไม่ ไม่คืนข้อมูลทีม | AC-3.3, AC-4.2 |

ข้อกำหนดของฟังก์ชัน:

1. create_team / join_team ต้องตรวจ auth.uid() ไม่เป็น NULL, profile มีอยู่ และผู้เรียกยังไม่มีทีม ไม่รับ owner_id, user_id หรือ role จากฟอร์ม
2. ล็อกแถว profile ของผู้เรียกก่อนตรวจสมาชิกและเขียนข้อมูล เพื่อให้คำขอที่ส่งพร้อมกันทำทีละคำขอ และมี PK ของ team_members เป็นข้อบังคับสุดท้าย ถ้ามีทีมแล้วคืนข้อความ “คุณมีทีมอยู่แล้ว” แม้เรียกข้ามหน้าจอ (AC-2.4)
3. create_team ทำทุกขั้นใน transaction (ชุดงานที่สำเร็จหรือยกเลิกพร้อมกัน) เดียวกัน ไม่เหลือทีมเปล่าหากเพิ่มหัวหน้าไม่สำเร็จ
4. join_team ค้น teams ภายในฟังก์ชัน ไม่สร้าง policy ให้คนนอกอ่าน teams หรือค้นรายชื่อทีม รหัสผิด/รูปแบบผิดคืน “ไม่พบทีมจากรหัสนี้” โดยไม่บอกรายละเอียดทีม รหัสถูกจะคืน team_id หลังเพิ่มสมาชิกแล้ว จากนั้นอ่านข้อมูลด้วย RLS ตามปกติ
5. ฟังก์ชันที่อ่าน teams / team_members เพื่อใช้ใน policy อยู่ใน schema private ที่ไม่เปิดเป็น API และอ่านด้วยสิทธิ์เจ้าของที่เหมาะสม เพื่อเลี่ยง policy เรียกวนกัน กำหนดสิทธิ์เรียกเฉพาะที่จำเป็น ห้ามรับ SQL หรือชื่อวัตถุอิสระ
6. ทุก SECURITY DEFINER ใช้ search_path ที่กำหนดตายตัวหรือว่าง และระบุ schema ของทุกตาราง ยกเลิก EXECUTE จาก PUBLIC / anon แล้วให้ authenticated เฉพาะฟังก์ชันที่ต้องใช้ เจ้าของฟังก์ชันต้องมีสิทธิ์เท่าที่จำเป็น
7. ไม่เปิดฟังก์ชันทั่วไปที่ข้าม RLS หรือเพิ่มสมาชิกคนอื่นได้ พิจารณาจำกัดความถี่การลองรหัสเมื่อพ้น workshop โดยไม่เปลี่ยนสิทธิ์การอ่านตาราง

## 5. กติกาที่บังคับในฐานข้อมูล

| กติกา | กลไกบังคับ | อ้างอิง |
|---|---|---|
| ชื่อผู้ใช้ ชื่อทีม ชื่องานห้ามว่าง | NOT NULL + CHECK หลังตัดช่องว่าง; ตรวจบน server เพื่อแสดงข้อความอ่านง่ายด้วย | AC-1.1, AC-2.5, AC-3.5 |
| หนึ่งคนอยู่ได้หนึ่งทีม | PK team_members.user_id + ฟังก์ชันล็อกแถวก่อนเขียน; ปิดเขียนตรง | AC-2.4 |
| หัวหน้าคือผู้สร้างและเป็นสมาชิกทีม | owner_id จาก auth.uid(), FK คู่แบบตรวจท้ายธุรกรรม, ปิดเปลี่ยนหัวหน้า | AC-2.2 |
| รหัสเชิญไม่ซ้ำและยาว 6 ตัว | unique + CHECK + สุ่มใหม่เมื่อชนกัน | AC-2.2, AC-2.3 |
| หัวหน้าเท่านั้นสร้างงาน | INSERT policy ตรวจทีมของผู้เรียกและ owner_id; trigger ตรวจซ้ำและตั้ง created_by | AC-3.3 |
| งานใหม่เริ่มยังไม่เริ่มเสมอ | default todo และ BEFORE INSERT trigger ปฏิเสธ status อื่น; ไม่พึ่ง default อย่างเดียว | AC-3.1 |
| มอบหมายได้เฉพาะสมาชิกในทีม รวมหัวหน้า | FK คู่ team_id / assignee_id บังคับทั้ง INSERT และ UPDATE | AC-3.1, AC-3.4 |
| ผู้รับงานที่ไม่ใช่หัวหน้าแก้ได้เฉพาะสถานะ | UPDATE policy จำกัดผู้รับ; BEFORE UPDATE trigger เทียบ OLD / NEW ทุกคอลัมน์ ยอมให้เปลี่ยน status และให้ trigger ตั้ง updated_at เท่านั้น | AC-4.3, AC-4.4 |
| หัวหน้าเปลี่ยนสถานะทุกงานในทีม | UPDATE policy + trigger ตรวจหัวหน้าจากทีมของแถวเดิม ไม่เชื่อ team_id ที่ส่งมา | AC-4.2 |
| ย้ายงานข้ามทีม / ปลอมผู้สร้างไม่ได้ | trigger ปฏิเสธเปลี่ยน id, team_id, created_by, created_at ทุกบทบาทผู้ใช้แอป | AC-3.7, AC-4.4 |
| สถานะถูกต้อง | CHECK เฉพาะสามค่า; เปลี่ยนข้ามขั้นหรือย้อนกลับได้ | AC-4.1 |
| ทีมอื่นอ่านข้อมูลไม่ได้ | SELECT policy ของทุกตาราง ตรวจทีมของ auth.uid() | AC-2.6, AC-3.7, NFR-1 |

การปฏิเสธสิทธิ์ต้องทำให้ไม่มีข้อมูลเปลี่ยนจริง ถ้า UPDATE ไม่พบแถวที่อนุญาตและคืน 0 แถว ให้ server แสดงว่าไม่มีสิทธิ์หรือไม่พบงาน ไม่แสดงว่าบันทึกสำเร็จ ไม่เปิดรายละเอียดงานทีมอื่นเพื่ออธิบายข้อผิดพลาด

## 6. หน้าจอและการทำงาน

| Route (ที่อยู่หน้าเว็บ) | เนื้อหา / การทำงาน | US / AC |
|---|---|---|
| / | เก็บหน้าตรวจการเชื่อมต่อเดิมได้ พร้อมลิงก์เข้าสู่ระบบหรือไปทีม ไม่แสดงข้อมูลส่วนบุคคล | บริบทเดิมของโปรเจกต์ |
| /login | สมัครด้วยชื่อ อีเมล รหัสผ่านอย่างน้อย 6 ตัวอักษร; ล็อกอินด้วยอีเมล/รหัสผ่าน; สำเร็จไป /team | US-1, AC-1.1–AC-1.2 |
| /team | ไม่มีทีม: ฟอร์มสร้างทีม/เข้าร่วมทีม; มีทีม: ชื่อทีม รหัสเชิญ รายชื่อและบทบาท ไม่แสดงฟอร์มเข้าทีมซ้ำ | US-2, AC-2.1–AC-2.6 |
| /tasks | กระดานงานสามสถานะ แสดงชื่อ ผู้รับ วันที่ไทย และรายละเอียดงาน; เฉพาะหัวหน้าเห็นฟอร์มสร้างงาน; ผู้รับหรือหัวหน้าเห็นตัวเปลี่ยนสถานะ | US-3, US-4, AC-3.1–AC-3.7, AC-4.1–AC-4.5 |
| /my | งานที่ assignee_id เป็นผู้ใช้ปัจจุบัน ซ่อนงาน done ตอนเปิดหน้า มีตัวเลือกแสดงงานที่เสร็จแล้วและเปลี่ยนสถานะ | US-5, AC-5.1–AC-5.4 |

- /team, /tasks และ /my ต้องตรวจผู้ใช้ฝั่ง server ก่อนอ่านข้อมูล ถ้ายังไม่ล็อกอินไป /login (AC-1.5) แม้ยังไม่ทำ US-5 เสร็จ route /my ก็ต้องไม่เปิดข้อมูลโดยไม่ตรวจผู้ใช้
- /tasks และ /my หากยังไม่มีทีมให้ไป /team; คำขอเปลี่ยนข้อมูลทุกครั้งตรวจใหม่ ไม่อาศัยแค่การตรวจตอนเปิดหน้า
- แถบบนทุกหน้าที่ล็อกอินแล้วแสดงชื่อและปุ่มออกจากระบบ; เมื่อออกให้ล้างสถานะที่แสดงข้อมูลผู้ใช้และกลับ /login (AC-1.3)
- AC-1.2 ใช้ข้อความ “อีเมลหรือรหัสผ่านไม่ถูกต้อง”; AC-2.5 “กรุณากรอกชื่อทีม”; AC-3.5 “กรุณากรอกชื่องาน”
- /tasks ว่างแสดง “ยังไม่มีงานในทีม”; /my ไม่มีงานที่ตรงตัวกรองแสดง “ยังไม่มีงานที่ได้รับมอบหมาย” พร้อมลิงก์ /tasks (AC-3.6, AC-5.3)
- สร้างงานแล้วอ่านผลจากฐานข้อมูลและแสดงในคอลัมน์ยังไม่เริ่ม เมื่อเปลี่ยนสถานะสำเร็จให้ย้ายคอลัมน์ทันทีหลังบันทึก หากล้มเหลวคงสถานะเดิมและแจ้งภาษาไทย (AC-3.1, AC-4.1)
- ไม่ต้องทำการอัปเดตพร้อมกันทุกเบราว์เซอร์อัตโนมัติในรอบนี้ เพื่อนร่วมทีมโหลดหน้าใหม่เพื่อดูข้อมูลล่าสุดได้
- /my เรียง due_date จากน้อยไปมากและ NULL อยู่ท้ายสุด ใช้ created_at และ id เป็นลำดับรองให้ผลคงที่ ค่าเริ่มต้นกรอง status != done (AC-5.1–AC-5.2)
- แสดงวันที่ด้วยรูปแบบไทยและป้าย “ไม่มีกำหนด” เมื่อไม่มีวันที่ ใช้ Asia/Bangkok หาวันนี้; เลยกำหนดเมื่อ due_date < วันนี้ และ status != done เท่านั้น วันครบกำหนดเองยังไม่เลยกำหนด ห้ามแปลง date ผ่านเวลา UTC จนวันคลาดเคลื่อน (AC-4.5)
- ทุกหน้ามีสถานะ “กำลังโหลด…”, ไม่มีข้อมูล และข้อผิดพลาดภาษาไทย; ปุ่มระหว่างบันทึกป้องกันการกดซ้ำ และไม่ล้างข้อมูลฟอร์มเมื่อบันทึกล้มเหลว (NFR-3)
- รองรับความกว้าง 375px โดยไม่มีการเลื่อนแนวนอน: กระดานสามคอลัมน์เรียงลงล่างบนจอแคบ ฟอร์ม/ปุ่ม/ชื่อยาวตัดบรรทัดได้ ใช้ข้อความสถานะควบคู่กับสี (NFR-4)

## 7. การส่งอีเมล US-6 (งานเสริม)

ใช้ SMTP (บริการส่งอีเมล) ของ Gmail ตาม requirements.md ด้วยบัญชีทดลองเฉพาะ แยกส่วนส่งอีเมลไว้ฝั่ง server ที่ใช้ Node.js runtime (สภาพแวดล้อมรันโค้ดฝั่งบริการ) เท่านั้น ไม่ส่งจากเบราว์เซอร์หรือ trigger ฐานข้อมูล

1. คำขอสร้างงานตรวจผู้ใช้และสร้างงานภายใต้ RLS ของผู้เรียกตาม US-3 รอฐานข้อมูลยืนยันว่าสำเร็จก่อนส่งอีเมล (AC-6.2)
2. ใช้ id งานที่เพิ่งสร้าง อ่านงาน ผู้รับจาก profiles.email ชื่อทีมและชื่อผู้มอบหมายจากฐานข้อมูล ไม่รับที่อยู่อีเมล ชื่อทีม หรือชื่อผู้มอบหมายจากฟอร์มมาใช้ส่ง ไม่สร้างช่องทางส่งอีเมลอิสระให้ผู้ใช้เลือกผู้รับ (AC-6.4)
3. ส่งและรอผลภายในคำขอเดียวกัน ไม่ปล่อยงานส่งอีเมลไว้เบื้องหลังหลังตอบกลับซึ่งอาจหยุดทำงานบน Vercel ตั้งเวลารอให้มีขอบเขตและสั้นกว่า 1 นาที ตรวจว่าระยะเวลารันที่ตั้งไว้รองรับก่อนเปิด US-6
4. หัวเรื่อง “งานใหม่: <ชื่องาน>”; เนื้อหามีชื่องาน วันกำหนดส่งหรือ “ไม่มีกำหนด” ชื่อทีม และชื่อผู้มอบหมาย ใช้ข้อความธรรมดาหรือแปลงอักขระพิเศษอย่างปลอดภัยเมื่อใช้ HTML (AC-6.1)
5. ถ้าส่งล้มเหลวหรือหมดเวลารอ ห้ามย้อนลบงาน แจ้ง “สร้างงานแล้ว แต่ส่งอีเมลแจ้งไม่สำเร็จ” และไม่ชวนกดสร้างซ้ำ (AC-6.3) ยังไม่มีระบบส่งซ้ำอัตโนมัติในรอบนี้
6. อ่าน GMAIL_USER / GMAIL_APP_PASSWORD จากค่าตั้งฝั่ง server ใน .env.local หรือ Vercel เท่านั้น ไม่เติม NEXT_PUBLIC_ ไม่เขียนลงโค้ดหรือ log และไม่ส่งค่ากลับเบราว์เซอร์ (AC-6.5, NFR-2)

AC-6.1 ต้องทดสอบกล่องจดหมายจริงว่าถึงภายใน 1 นาที; การที่ SMTP รับข้อความสำเร็จยังไม่ยืนยันเวลาที่ผู้รับเห็น หากเกินเวลาต้องรายงานว่าเกณฑ์นี้ยังไม่ผ่าน ไม่อ้างว่ารับประกันได้จากการส่งคำขออย่างเดียว

## 8. แนวทางตรวจรับและลำดับพัฒนา

ยังไม่ต้องรัน lint/build สำหรับการเพิ่มเอกสารนี้ เมื่อพัฒนาโค้ดให้ตรวจ npm run lint และ npm run build ตามคำสั่งที่มีจริง ไม่มีคำสั่ง npm test ในโปรเจกต์ปัจจุบัน ตรวจเกณฑ์ยอมรับบนเว็บและด้วย publishable key ภายใต้บัญชีผู้ใช้จริง ไม่ใช้ผลจาก Table Editor เป็นหลักฐานว่า RLS ป้องกันได้

| ขั้น | งานพัฒนา / เกณฑ์ที่ต้องตรวจ |
|---|---|
| US-1 | สร้าง profiles และ trigger สมัคร; หน้า /login; สมัครสำเร็จ ชื่อถูกต้อง รหัสผิด ออกจากระบบ เปิดเบราว์เซอร์ใหม่ และ route ที่ต้องล็อกอิน ตาม AC-1.1–AC-1.5 |

| US-3 | tasks / กฎฐานข้อมูล / กระดานงาน; A มอบงานให้ B และตัวเอง; B สร้างไม่ได้; assignee ของ C ถูกปฏิเสธ; ทีมว่าง/ไม่มีทีม/ชื่อว่าง ตาม AC-3.1–AC-3.7 |

| ทุกขั้น | ตรวจ RLS ทุกตาราง ค่าลับ สถานะหน้าจอ และมือถือ 375px ตาม NFR-1–NFR-4 |

กรณีสำคัญด้านสิทธิ์: C query teams / team_members / profiles ของ A หรือ B แล้วไม่เห็นข้อมูล; A และ B query tasks ของทีม 2 แล้วไม่เห็นงาน; ผู้ไม่ล็อกอินอ่านทุกตารางไม่ได้ ทดสอบแก้ข้อมูลโดยไม่ผ่านปุ่มบนหน้าจอด้วย และยืนยันว่าแถวเดิมไม่ถูกเปลี่ยน

## 9. สมมติฐานและการตัดสินใจในการออกแบบ
