# วิธีทดสอบ US-2 ถึง US-4

รอบนี้เพิ่มทีม การสร้าง/มอบหมายงาน และเปลี่ยนสถานะตาม docs/requirements.md ไม่เพิ่มการแก้/ลบงานบนหน้าเว็บ US-5 และอีเมล US-6 ยังไม่อยู่ในรอบนี้

## 1. เตรียมฐานข้อมูลและเปิดเว็บ

1. ถ้ายังไม่เคยรัน SQL ของ US-1 ให้รัน supabase/migrations/20261114000100_us1_profiles.sql ก่อน ถ้ารันสำเร็จแล้วห้ามรันซ้ำ
2. เปิด supabase/migrations/20261114000200_us2_teams.sql ใน VS Code → คัดลอกทั้งหมด → Supabase → SQL Editor → New query → วาง → Run
3. ทำแบบเดียวกันกับ supabase/migrations/20261114000300_us3_us4_tasks.sql โดยรันหลัง US-2 สำเร็จเท่านั้น ทั้งสองไฟล์ออกแบบให้รันครั้งเดียว หากมีตารางชื่อซ้ำให้หยุดและแจ้งข้อผิดพลาด ไม่ลบตารางหรือปิด RLS เพื่อแก้
4. ไม่ต้องเพิ่มค่าตั้งใหม่ ใช้ NEXT_PUBLIC_SUPABASE_URL / NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY ใน .env.local เดิมเท่านั้น ห้ามใช้ secret key
5. เปิด Terminal ใน track-task-week10 → พิมพ์ npm run dev → เปิด http://localhost:3000/login หากมีเว็บรันอยู่แล้วให้ใช้เว็บเดิมหรือหยุดคำสั่งเดิมก่อน ไม่เปิดหลายตัวโดยไม่จำเป็น

## 2. เตรียมสามบัญชี

| บัญชี | เปิดผ่าน | หน้าที่ |
|---|---|---|
| A | หน้าต่างปกติ | สร้างทีม 1 เป็นหัวหน้าทีม |
| B | หน้าต่างไม่ระบุตัวตน | เข้าร่วมทีม 1 ด้วยรหัสจาก A |
| C | อีกเบราว์เซอร์หรืออีกโปรไฟล์ | สร้างทีม 2 เป็นคนนอกทีม 1 |

ใช้ชื่อและอีเมลต่างกัน หากบัญชีมีทีมแล้วจะย้ายหรือออกจากทีมไม่ได้ตามขอบเขต ใช้บัญชีทดสอบใหม่แทน การทดสอบ “ยังไม่มีทีม” ต้องทำก่อนสร้าง/เข้าทีม หรือใช้บัญชีใหม่เพิ่มเติม

| เกณฑ์ | ทำอะไร | ผลที่ต้องได้ |
|---|---|---|
| AC-2.1 | A ที่ยังไม่มีทีมเปิด /team | เห็นฟอร์ม “สร้างทีม” และ “เข้าร่วมทีม” |
| AC-2.5 | ส่งชื่อทีมว่างหรือมีแต่ช่องว่าง | ขึ้น “กรุณากรอกชื่อทีม” และไม่สร้างทีม |
| AC-2.2 | A สร้างทีม 1 | แสดงชื่อทีม รหัสเชิญ 6 ตัว รายชื่อ A บทบาทหัวหน้า |
| AC-2.3 รหัสผิด | B ลองรหัสไม่ถูกต้องก่อนเข้าทีม | ขึ้น “ไม่พบทีมจากรหัสนี้” ไม่แสดงข้อมูลทีมอื่น |
| AC-2.3 สำเร็จ | B ใส่รหัสเชิญของ A | เห็นทีม 1 และรหัสเดียวกัน A เป็นหัวหน้า B เป็นสมาชิก; A โหลดหน้าใหม่เห็น B |

AC-2.4 ต้องตรวจคำขอข้ามหน้าจอด้วย ชุด SQL ในข้อ 6 ตรวจว่าฟังก์ชันสร้างและเข้าทีมซ้ำคืน ALREADY_IN_TEAM ซึ่งแอปแปลงเป็น “คุณมีทีมอยู่แล้ว” การอยู่ทีมเดียวบังคับด้วยคีย์สมาชิกและการล็อกคำขอของผู้ใช้ในฐานข้อมูล

## 6. ตรวจสิทธิ์ฐานข้อมูลจริงโดยไม่ผ่านหน้าจอ

Table Editor ใช้สิทธิ์ผู้ดูแลจึงเห็นข้อมูลทุกทีม ไม่ใช้ผลจากหน้านั้นเป็นหลักฐานว่า RLS (กฎจำกัดสิทธิ์รายแถว) ป้องกันได้

1. หลังเตรียม A/B ทีม 1 และ C ทีม 2 แล้ว ไป Supabase → Authentication → Users → คัดลอก User UID ของแต่ละบัญชี ไม่ต้องคัดลอก key หรือรหัสผ่าน
2. เปิด supabase/tests/us2_us4_permissions.sql คัดลอกทั้งหมดไป SQL Editor → New query
3. ในช่อง query เปลี่ยน REPLACE_WITH_A_USER_UUID, REPLACE_WITH_B_USER_UUID และ REPLACE_WITH_C_USER_UUID เป็น UID จริง ให้คงเครื่องหมายคำพูดเดิมไว้ ไม่ต้องบันทึก UID จริงลงไฟล์ใน Git
4. กด Run ทั้งชุด ต้องไม่มี error และมีผล PASS ในชุดผลลัพธ์ของคำสั่ง SELECT ก่อน ROLLBACK (Supabase อาจแสดงผลสุดท้ายเป็นสำเร็จ ให้ดูผลลัพธ์ของ SELECT ด้วย)
5. ชุดนี้สร้างงานทดสอบชั่วคราวแล้ว ROLLBACK (ยกเลิกการเปลี่ยนแปลงทั้งหมดในชุด) จึงไม่ทิ้งงานทดสอบไว้ ถ้ามี error ให้รัน ROLLBACK; ใน query ใหม่ก่อนลองอีกครั้ง และส่งข้อความ error ให้ Codex โดยไม่ส่งค่าลับ

ชุดตรวจใช้บทบาท authenticated (สิทธิ์ของผู้ใช้ล็อกอิน) พร้อมตัวตน A/B/C เพื่อทดสอบ RLS จริง ตรวจ AC-2.4, AC-2.6, AC-3.3, AC-3.4, AC-3.7 และ AC-4.1–AC-4.4 รวมการเทียบข้อมูลเดิมหลังคำขอถูกปฏิเสธ ไม่ได้ใช้สิทธิ์ผู้ดูแลทดสอบการอ่าน/เขียน และไม่ใช่การทดสอบ publishable key ผ่านเครือข่ายจริง

ถ้าต้องตรวจเส้นทาง publishable key เพิ่ม ให้ผู้พัฒนาเรียก Supabase API ด้วย key สาธารณะและสถานะล็อกอินของแต่ละบัญชี: query teams / team_members / profiles / tasks ต้องเห็นเฉพาะแถวที่อนุญาต; ลองสร้างโดย B มอบให้ C และเปลี่ยนฟิลด์อื่นโดย B ต้องถูกปฏิเสธ ห้ามใช้ secret key หรือ token ผู้ดูแล และห้ามนำ token จริงไปวางในแชท
